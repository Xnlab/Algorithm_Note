# '좋은 수' 구하기 (백준 1253 좋다)

- **출처**: Do it! 알고리즘 코딩테스트 with 파이썬 — 투 포인터 / 백준 1253
- **유형**: 투 포인터 (정렬 + 양 끝에서 좁히기, 수마다 반복)
- **푼 날짜**: 2026-11-13
- **결과**: 오답 (예제만 우연히 통과) → 같은 날 다시 풀어 **정답**

## 문제 요약
수 N개(N ≤ 2,000, 값은 −10⁹ ~ 10⁹, **음수·0·중복 가능**)에서, 어떤 수가 **자기 자신이 아닌 서로 다른 두 수의 합**으로 나타나면 그 수는 '좋은 수'다. 좋은 수의 개수를 구한다. 값이 같아도 위치가 다르면 다른 수다.

## 떠올렸어야 할 단서
- "어떤 수 = 다른 두 수의 합" → 수 하나마다 **두 수의 합 찾기**(주몽의 명령) → 정렬 + 양 끝 투 포인터를 **N번** 반복
- N ≤ 2,000 → 수마다 O(N) 투 포인터 × N번 = O(N²) = 400만 → 가능
- 값에 **음수와 0**이 있음 → 두 수가 목표 수보다 **뒤쪽(더 큰 수)**에 있을 수도 있다. 예: 5 = 7 + (−2)
- "서로 다른 두 수", "자기 자신 제외" → 같은 위치를 두 번 쓰거나 목표 수 자신을 쓰면 안 된다

## 내 풀이

```python
n = int(input())
a = list(map(int, input().split()))
target = n - 1
e = target - 1
s = 0
count = 0
while target != 1:
    if a[s] + a[e] == a[target]:
        target -= 1
        e = target - 1
        s = 0
        count += 1
    elif a[s] + a[e] > a[target]:
        e -= 1
    else:
        s += 1

print(count)
```

- 아이디어: 맨 뒤 수부터 목표로 삼고, 그 앞 구간 [0, target−1]에서 양 끝 투 포인터로 두 수를 찾는다. 찾으면 다음 목표로 넘어간다.
- 평가: "목표 수마다 양 끝 투 포인터"라는 큰 방향은 맞다. 하지만 아래 버그 때문에 대부분의 입력에서 오류가 나거나 틀린다.

### 버그 목록

| # | 문제 | 결과 | 예 |
|---|---|---|---|
| 1 | **못 찾았을 때** 다음 목표로 넘어가는 처리가 없음. `s`와 `e`가 엇갈린 뒤에도 계속 움직임 | `e`가 음수가 되거나 `s`가 범위를 넘어 `IndexError` | `1 2 5` → `IndexError` (5는 좋은 수가 아님) |
| 2 | `s == e`일 때도 합을 확인함 → **같은 수를 두 번** 사용 | 좋은 수가 아닌데 셈 | `1 2 4` → 1 (2+2=4로 셈, 정답 0) |
| 3 | 입력을 **정렬하지 않음** | 투 포인터의 전제가 깨짐 | `10 9 … 1` → `IndexError` |
| 4 | 두 수를 목표 **앞쪽**에서만 찾음 | 음수·0이 있으면 뒤쪽 수와의 합을 놓침 | `0 0 0` → 1 (정답 3) |
| 5 | 반복이 `target == 1`에서 끝남 → 0번, 1번 위치는 검사 안 함 | 4번과 같은 이유로 앞쪽 수도 좋은 수일 수 있음 | `0 0 0`의 앞 두 개 |

### 버그별 영향 (직접 실행해서 확인)
- 예제 `1 2 … 10`이 맞은 이유: 정렬되어 있고, 3 ~ 10이 **모두** 앞의 두 수 합으로 만들어져서 "못 찾는 경우"(버그 1)가 한 번도 생기지 않았다.
- 길이 1 ~ 10, 값 −5 ~ 10의 무작위 입력 1,000개: **정답 95개**, 오답 24개, `IndexError` 881개
- 정렬된 서로 다른 양수만 넣어도 1,000개 중 정답 13개 (대부분 버그 1로 `IndexError`)

## 정답 풀이 (책 풀이 방식)

```python
n = int(input())
a = list(map(int, input().split()))
a.sort()                       # 투 포인터를 위해 정렬
count = 0

for k in range(n):             # 모든 수를 한 번씩 목표로
    find = a[k]
    i = 0                      # 두 수는 배열 전체에서 찾는다
    j = n - 1
    while i < j:               # 위치 비교 → 같은 수를 두 번 쓰지 않음
        if a[i] + a[j] == find:
            if i != k and j != k:      # 목표 수 자신은 제외
                count += 1
                break                  # 좋은 수 확정 → 다음 목표로
            elif i == k:
                i += 1                 # 목표 자신을 건너뜀
            elif j == k:
                j -= 1
        elif a[i] + a[j] < find:
            i += 1
        else:
            j -= 1
    # while이 끝날 때까지 못 찾았으면 좋은 수가 아님 → 자연스럽게 다음 k로

print(count)
```

- 시간복잡도: **O(N²)** (목표 N개 × 투 포인터 O(N))

## 다시 푼 풀이 (2026-11-13, 정답)

```python
n = int(input())
a = list(map(int, input().split()))
a.sort()
count = 0

for k in range(n):
    find = a[k]
    i = 0
    j = n - 1
    while i < j:
        if a[i] + a[j] == find:
            if i != k and j != k:
                count += 1
                break
            elif i == k:
                i += 1
            elif j == k:
                j -= 1
        elif a[i] + a[j] > find:
            j -= 1
        else:
            i += 1
    
print(count)
```

- 정렬, 목표마다 배열 전체에서 찾기, `while i < j`, 목표 자신 제외, `break`까지 버그 1~5를 모두 고쳤다.
- 정답 풀이와 비교해 `>`와 `<` 분기의 순서만 다르다. 세 경우(같음 / 큼 / 작음)가 서로 겹치지 않으므로 순서는 결과에 영향이 없다.
- 무작위 1,000개(음수·0·중복 포함) 전부 정답, 반례 `0 0 0` → 3, `1 2 4` → 0, `1 2 5` → 0, N = 2,000 → 로컬 약 0.7초

## 해설

### 내 풀이와 무엇이 다른가

| | 내 풀이 | 정답 풀이 |
|---|---|---|
| 목표 고르기 | `while`에서 target을 직접 줄임 | `for k in range(n)`으로 **모든 수** |
| 두 수를 찾는 범위 | 목표 **앞쪽** [0, target−1] | 배열 **전체** [0, n−1] |
| 못 찾았을 때 | 처리 없음 → 포인터가 범위 밖으로 | `while i < j`가 끝나면 다음 k로 |
| 같은 수 두 번 | `s == e`도 확인 | `i < j`라서 불가능 |
| 목표 자신 | 앞쪽만 보니 자동 제외 | `i != k and j != k`로 직접 제외 |

핵심은 **"찾는 반복"과 "목표를 바꾸는 반복"을 분리**한 것이다. 바깥 `for`가 목표를 하나씩 정하고, 안쪽 `while i < j`가 그 목표에 대해 찾기를 끝까지 한다. 찾으면 `break`, 못 찾으면 `while`이 자연히 끝나서 둘 다 다음 목표로 넘어간다. 내 풀이는 반복이 하나뿐이라 "찾았을 때"만 다음 목표로 가는 길이 있고, "못 찾았을 때" 가는 길이 없었다.

### 왜 배열 전체에서 찾아야 하는가
- 양수만 있으면 두 수의 합은 각 수보다 크니까, 목표의 두 수는 목표보다 작고 정렬 후 **앞쪽**에만 있다. 내 풀이는 이 경우만 생각했다.
- 하지만 이 문제는 음수와 0이 있다.
  - 정렬된 `-2 3 5 7`: 5 = 7 + (−2) → 7은 5보다 **뒤**에 있다.
  - `0 0 0`: 각 0 = 나머지 두 0의 합 → 맨 앞 0도 좋은 수. 답 3.
- 그래서 두 수는 목표 위치와 상관없이 **배열 전체**에서 찾고, 목표 자신만 빼야 한다.

### `i == k`이면 왜 i만 옮기는가
- 합이 맞았는데 그중 하나가 목표 자신이면 그 조합은 쓸 수 없다. 목표 자신을 가리키는 포인터만 한 칸 옮겨서 **다른 조합을 계속 찾는다.**
- 예: `0 0 0`, k = 0 → i = 0, j = 2: 0 + 0 = 0인데 i == k → i = 1 → i = 1, j = 2: 0 + 0 = 0, 둘 다 k가 아님 → 좋은 수.

### 주몽의 명령과 비교
| | 주몽의 명령 | 좋은 수 |
|---|---|---|
| 찾는 것 | 합이 M인 쌍의 **개수** | 합이 a[k]인 쌍이 **있는지** |
| 투 포인터 횟수 | 1번 | 목표마다 1번, 총 **N번** |
| 찾았을 때 | 세고 양쪽 이동, 계속 | 세고 `break` |
| 추가 조건 | 없음 | 목표 자신(k) 제외 |

### 예제 일부 따라가기
`-2 3 5 7` (정렬 후), 목표 k = 2 (값 5):

| i | j | a[i] + a[j] | 판단 |
|---|---|---|---|
| 0 (−2) | 3 (7) | 5 | 같음, i ≠ 2, j ≠ 2 → **좋은 수**, break |

내 풀이였다면 목표 5의 앞쪽 [−2, 3]만 보므로 −2 + 3 = 1 → 찾지 못하고 포인터가 범위를 벗어난다.

## 검증
- 예제 `1 ~ 10` → 정답 풀이 `8`
- 길이 1 ~ 10, 값 −5 ~ 10(중복 포함) 무작위 1,000개에서 정답 풀이는 모든 조합을 직접 확인한 결과와 전부 일치
- N = 2,000, 값 −10⁹ ~ 10⁹ → 정답 풀이 로컬 약 0.8초

## 배운 점
- 투 포인터를 **목표마다 반복**할 때는 바깥 반복(목표 고르기)과 안쪽 반복(찾기)을 분리한다. 안쪽은 `while i < j`로, **못 찾는 경우에도 끝나도록** 쓴다.
- 문제의 값 범위에 **음수·0**이 있으면 "합은 각 수보다 크다"는 양수 직관이 깨진다. 찾는 범위를 좁히기 전에 값 범위를 확인한다.
- 투 포인터 종료 조건은 **위치 비교 `i < j`** (주몽에서 배운 것). 이게 같은 수를 두 번 쓰는 것도 막아 준다.
- 예제가 맞아도, **답이 없는 경우**(못 찾는 경우)를 하나 직접 넣어 본다.
